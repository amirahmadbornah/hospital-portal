# پورتال داخلی بیمارستان — نسخه ۲.۰

پورتال اصلی (چیزی که کاربران عادی می‌بینند) همچنان یک صفحه کاملاً
استاتیک است: HTML5 + CSS3 + Vanilla JavaScript (ES6) + JSON — بدون
فریم‌ورک، بدون دیتابیس، بدون فرآیند Build. این بخش با کپی کردن پوشه
روی سرور Nginx آماده استفاده است.

از نسخه ۱۲.۳.۰ (و توسعه‌یافته در v2.0) یک **پنل مدیریت اختیاری** هم
اضافه شده (`/admin/`) که برای کار کردن به PHP-FPM نیاز دارد — جزئیات
کامل در بخش «پنل مدیریت لینک‌ها» پایین‌تر. اگر این پنل را نصب نکنید،
پورتال اصلی دقیقاً مثل قبل، کاملاً استاتیک و بدون بک‌اند کار می‌کند
(به‌جز دکمه «ورود مدیر» در هدر که در این حالت فقط غیرفعال می‌ماند و
هیچ خطایی نشان نمی‌دهد).

## استقرار (Deployment)

1. کل پوشه `Portal/` را در سرور Ubuntu، مثلاً در مسیر `/var/www/portal` قرار دهید.
2. فایل `nginx.portal.conf` را در `/etc/nginx/sites-available/portal` کپی و فعال کنید
   (دستورات دقیق داخل خود فایل نوشته شده است).
3. نام `portal` و/یا `portal.local` را در DNS داخلی یا در فایل hosts کلاینت‌ها
   به IP سرور متصل کنید.
4. `sudo nginx -t && sudo systemctl reload nginx`

از این پس هر کاربر با مراجعه به `http://portal` آخرین نسخه پورتال را می‌بیند —
بدون نصب محلی و بدون کپی فایل روی دستگاه‌ها.

## پنل مدیریت (v2.0 — لینک‌ها + اعلان‌ها)

یک پنل تحت وب در مسیر `/admin/` اضافه شد که مدیر شبکه می‌تواند از آن
هم لینک‌های پرتال (ایجاد، ویرایش، حذف، فعال/غیرفعال، درگ‌اند‌دراپ) و
هم اعلان‌ها (بخش «سیستم اعلان‌ها» پایین‌تر را ببینید) را مدیریت کند —
بدون دسترسی SSH و بدون ویرایش دستی JSON. **در پنل لینک‌ها فقط
لینک‌ها** مدیریت می‌شوند؛ دسته‌بندی‌ها (`categories`) فقط برای انتخاب
در فرم خوانده می‌شوند و از این پنل قابل ساخت/ویرایش نیستند (دقیقاً
طبق دامنه‌ی درخواستی).

### این پنل چطور کار می‌کند (و چرا یک بک‌اند لازم شد)

هش bcrypt، Session با کوکی HttpOnly/Secure، CSRF Token و نوشتن روی
`links.json`/`announcements.json` همگی ذاتاً نیازمند کد سمت سرور
هستند — با HTML/CSS/JS خالص غیرممکن‌اند. برای همین یک بک‌اند PHP سبک
(بدون فریم‌ورک، بدون دیتابیس) اضافه شد که فقط پشت `/api/` و `/admin/`
زندگی می‌کند و به هیچ‌وجه به پورتال اصلی دست نمی‌زند:

```
admin/
  ├── login.html, dashboard.html, admin.js/css       ← پنل لینک‌ها
  └── announcements.html, announcements-admin.js      ← پنل اعلان‌ها (v2.0)
api/
  ├── bootstrap.php    ← Session/CSRF/Backup/Audit-log مشترک بین همه
  ├── auth.php         ← ورود/خروج/بررسی نشست
  ├── links.php        ← CRUD کامل لینک‌ها
  └── announcement.php ← CRUD کامل اعلان‌ها + آپلود تصویر (v2.0)
config/config.php       ← تنها یک حساب مدیر؛ رمز به‌صورت bcrypt هش می‌شود
data/backups/           ← نسخه پشتیبان خودکار قبل از هر ذخیره (حداکثر ۲۰ نسخه هرکدام)
data/audit.log          ← لاگ هر عملیات: تاریخ، ساعت، کاربر، عملیات، هدف، IP
data/uploads/           ← تصاویر آپلودشده برای اعلان‌ها (v2.0)
```

### راه‌اندازی اولیه (این مراحل الزامی‌اند)

```bash
# ۱. نصب PHP-FPM روی سرور Ubuntu
sudo apt install php-fpm php-json

# ۲. بررسی نسخه/مسیر سوکت PHP-FPM و هماهنگی با nginx.portal.conf
ls /run/php/
# اگر نسخه با php8.3-fpm.sock در nginx.portal.conf فرق داشت، همان‌جا اصلاح کنید

# ۳. تولید رمز عبور واقعی مدیر (هش پیش‌فرض عمداً نامعتبر است — ورود با آن ممکن نیست)
cd /var/www/portal
php admin/generate-password-hash.php
# مقدار خروجی را در config/config.php به‌جای passwordHash بگذارید

# ۴. اجازه نوشتن به وب‌سرور بدهید (کاربر PHP-FPM معمولاً www-data است)
# شامل data/uploads/ هم می‌شود — بدون این، آپلود تصویر اعلان با خطا مواجه می‌شود.
sudo chown -R www-data:www-data /var/www/portal/data
sudo chmod -R 750 /var/www/portal/data

# ۵. فعال‌سازی نهایی
sudo nginx -t && sudo systemctl reload nginx
sudo systemctl restart php8.3-fpm
```

بعد از این مراحل، پنل روی `http://portal/admin/login.html` در دسترس
است (یا با کلیک روی «🔐 ورود مدیر» در هدر خود پرتال). نام کاربری
پیش‌فرض `admin` است (در `config/config.php` قابل تغییر).

### نکته امنیتی مهم — همان موضوع HTTPS قبلی

Session Cookie با پرچم `Secure` ساخته می‌شود، اما این پرچم را کد
به‌صورت **خودکار فقط وقتی درخواست واقعاً روی HTTPS باشد** فعال
می‌کند (`isRequestSecure()` در `api/bootstrap.php`) — چون اگر
همیشه فعال می‌بود، روی دیپلوی HTTP فعلی شما (`http://192.168.184.29:8080/`)
کوکی اصلاً برای مرورگر قابل استفاده نبود و ورود همیشه شکست می‌خورد.

یعنی پنل همین الان هم روی HTTP کار می‌کند، اما نام کاربری/رمز عبور و
کوکی نشست بدون رمزنگاری روی شبکه رد و بدل می‌شوند — برای تست داخلی
قابل قبول، برای استفاده واقعی روزانه **باید** طبق راهنمای بخش «نصب
PWA» بالاتر یک گواهی HTTPS داخلی راه‌اندازی کنید. همان تنظیم HTTPS
هم مشکل نصب PWA را حل می‌کند، هم این پنل را واقعاً امن می‌کند.

### محدودیت‌های عمدی (طبق دامنه‌ی درخواستی)

- فقط یک حساب مدیر وجود دارد؛ هیچ Role یا کاربر دیگری نیست.
- مدت نشست ۳۰ دقیقه بدون فعالیت است، بعدش باید دوباره وارد شوید.
- پنل کاملاً از PWA و Service Worker پورتال اصلی مستثنا شده — نه
  صفحاتش (`/admin/`) و نه پاسخ‌های API آن (`/api/`) هیچ‌وقت کش
  نمی‌شوند، حتی بعد از ورود (دقیقاً طبق «Service Worker نباید
  پاسخ‌های API را Cache کند» — برای سادگی و امنیت بیشتر، تصمیم
  گرفتیم پنل ادمین را اصلاً وارد چرخه کش PWA نکنیم، نه اینکه فقط بعد
  از ورود کش شود). تصاویر آپلودشده در `data/uploads/` این استثنا را
  ندارند و عادی کش می‌شوند — چون فایل‌های عمومی و بدون نشست هستند و
  هر آپلود نام فایل جدیدی می‌گیرد.

## به‌روزرسانی محتوا (بدون تغییر HTML)

| برای این تغییر... | فقط این فایل را ویرایش کنید |
|---|---|
| افزودن/حذف/ویرایش یک لینک | `data/links.json` |
| افزودن یک دسته‌بندی جدید | `data/links.json` (آرایه `categories`) |
| تغییر متن یا وضعیت اعلان | `data/announcement.json` |
| تغییر شماره نسخه، نام بیمارستان، بازه رفرش | `data/config.json` |

فایل‌های JSON بدون کش مرورگر خوانده می‌شوند (`Cache-Control: no-store`)،
پس تغییرات حداکثر تا بازه رفرش خودکار (پیش‌فرض ۵ دقیقه، در `config.json`)
برای همه کاربران باز است — بدون رفرش دستی صفحه.

### ساختار هر لینک در `links.json`

```json
{
  "id": "his-005",
  "title": "عنوان سیستم",
  "description": "توضیح کوتاه",
  "url": "http://example.portal.local",
  "category": "his",
  "icon": "clipboard",
  "color": "#14B8A6",
  "order": 5,
  "enabled": true,
  "new": false,
  "favoriteAllowed": true
}
```

آیکون‌های موجود در `assets/js/app.js` (شیء `ICONS`) تعریف شده‌اند: در صورت
نیاز به آیکون جدید، یک ورودی SVG کوچک به همان شیء اضافه کنید.

## مدیریت کش (Cache Busting)

- فایل‌های `data/*.json` همیشه با پارامتر زمان (`?t=timestamp`) و
  `cache: 'no-store'` خوانده می‌شوند تا هرگز از کش مرورگر یا Nginx خوانده نشوند.
- فایل‌های `assets/css` و `assets/js` با پارامتر نگارش (`?v=12.0.0`) در
  `index.html` بارگذاری می‌شوند. هنگام هر تغییر در کد (نه محتوای JSON)، این
  عدد را هم در `index.html` و هم در `data/config.json` افزایش دهید تا
  مرورگرها نسخه جدید را دریافت کنند.

## فونت IRANSans

فونت IRANSans دارای مجوز تجاری است و در این پروژه توزیع نشده است.
فایل‌های `.woff2` را با نام‌های زیر در `assets/fonts/` قرار دهید:

```
IRANSansX-Regular.woff2
IRANSansX-Medium.woff2
IRANSansX-Bold.woff2
```

تا زمانی که این فایل‌ها اضافه نشده‌اند، پورتال به‌طور خودکار به فونت آزاد
Vazirmatn (با ظاهر مشابه) سوییچ می‌کند؛ فایل‌های آن را نیز می‌توانید از
[rastikerdar/vazirmatn](https://github.com/rastikerdar/vazirmatn) دانلود
و با همان نام‌گذاری در `assets/fonts/` قرار دهید تا حتی بدون IRANSans،
ظاهر نهایی صحیح باشد.

## داده‌های ذخیره‌شده در دستگاه کاربر (LocalStorage)

فقط و فقط این پنج مورد، و هیچ‌چیز دیگر:

- موردعلاقه‌ها (`hp12:favorites`)
- اخیراً استفاده‌شده‌ها (`hp12:recent`, حداکثر ۱۰ مورد)
- آمار پرکاربردترین‌ها (`hp12:stats`)
- تنظیم پوسته روشن/تیره (`hp12:theme`)
- آخرین «دور» بسته‌شده‌ی هر اعلان زمان‌دار (`hp12:announcementDismiss`)

هیچ اطلاعات کاربری، هیچ کوکی و هیچ ارتباط با سرویس بیرونی وجود ندارد.

## سیستم اعلان‌ها (v2.0 — بازطراحی کامل)

سیستم قبلی (یک بنر ساده از `data/announcement.json` با تکرار
ساعتی) **کاملاً جایگزین شده**. حالا:

- چند اعلان هم‌زمان ممکن است فعال باشند (`data/announcements.json`،
  آرایه‌ای از اعلان‌ها).
- هر اعلان می‌تواند فقط‌متن، فقط‌تصویر یا متن+تصویر باشد.
- سه سطح اولویت: عادی، مهم، بحرانی — بحرانی همیشه اول نمایش داده
  می‌شود.
- هر اعلان بازه‌ی زمانی مستقل خودش را دارد (تاریخ شروع/پایان)؛ خارج
  از این بازه خودکار مخفی می‌شود.
- دو حالت نمایش: **Banner** (بالای صفحه، اگر چند تا باشند به‌صورت
  Slider با نقطه‌های ناوبری و Auto Slide) یا **Popup** (Modal
  تمام‌صفحه، یکی‌یکی به ترتیب اولویت).
- `dismissible`: کاربر می‌تواند ببندد یا نه.
- `showOnce`: فقط یک‌بار برای هر کاربر (بر اساس LocalStorage) نمایش
  داده شود.
- اگر هیچ اعلان فعالی نباشد، هیچ Banner/Placeholder خالی نمایش داده
  نمی‌شود — صفحه کاملاً تمیز می‌ماند.

مدیریت این اعلان‌ها **فقط از طریق پنل مدیریت** انجام می‌شود
(`/admin/announcements.html`، لینک «مدیریت اعلان‌ها» در هدر پنل) —
دیگر نیازی به ویرایش دستی JSON نیست. آپلود تصویر (PNG/JPG/WEBP، حداکثر
۵ مگابایت) مستقیماً از همان فرم انجام می‌شود؛ فایل‌ها در
`data/uploads/` با نام‌های تصادفی سرور-تولیدشده ذخیره می‌شوند (نام
فایل اصلی هرگز اعتماد نمی‌شود، برای جلوگیری از Path Traversal).

### دکمه ورود مدیر در هدر پرتال (v2.0)

دکمه «متصل» قبلی از هدر حذف شد. حالا سمت چپ هدر:

- اگر مدیر وارد نشده: دکمه **🔐 ورود مدیر** — کلیک روی آن یک Modal
  ورود همان‌جا (بدون خروج از پرتال) باز می‌کند.
- بعد از ورود موفق: دکمه به **👤 مدیر سیستم** تغییر می‌کند؛ کلیک روی
  آن یک منوی کشویی با «داشبورد مدیریت» و «خروج» باز می‌کند.
- اگر بک‌اند PHP اصلاً نصب نشده باشد، این دکمه بی‌صدا در حالت «ورود
  مدیر» می‌ماند و هیچ خطایی به کاربر عادی نشان داده نمی‌شود (سازگاری
  کامل با پورتال بدون بک‌اند).

### API جدید: `api/announcement.php`

همان سطح امنیتی `api/links.php` را دارد (Session، CSRF، Sanitize):

| Action | Method | توضیح |
|---|---|---|
| `list` | GET | تمام اعلان‌ها (فیلتر/مرتب‌سازی سمت کلاینت در پنل) |
| `create` | POST | ایجاد اعلان جدید |
| `update` | POST یا PUT | ویرایش (PUT فقط برای تغییرات بدون تصویر جدید) |
| `delete` | POST یا DELETE | حذف (تصویر مرتبط هم پاک می‌شود) |
| `toggle` | POST | فعال/غیرفعال سریع |
| `upload` | POST (multipart) | آپلود تصویر، خروجی مسیر برای استفاده در create/update |

## رفع مشکل مصرف بی‌رویه حافظه/کش (v12.2.1)

**علت واقعی کندی و فشار روی سیستم‌های ضعیف:** ربطی به Link Health
Checker نداشت — مشکل در `service-worker.js` بود. برای اینکه فایل‌های
`data/*.json` همیشه تازه بمانند، هر درخواست با یک پارامتر یکتا مثل
`?t=۱۷۵۳۶۹۰۰۰۰` ارسال می‌شود (کد قبلی هم همین‌طور بود). اما Service
Worker این آدرس‌های یکتا را عیناً در Cache Storage ذخیره می‌کرد —
یعنی به‌جای جایگزین‌کردن یک رکورد، هر ۵ دقیقه (بازه پیش‌فرض رفرش) **۴
رکورد جدید** به کش اضافه می‌شد، برای همیشه، تا وقتی تب پورتال باز
بود. روی سیستم‌هایی که پورتال ساعت‌ها یا تمام روز باز می‌ماند (دقیقاً
سناریوی کیوسک/ایستگاه پرستاری)، این کش به‌مرور صدها و هزاران رکورد
اضافه پیدا می‌کرد و فشار حافظه/دیسک واقعی ایجاد می‌کرد.

**راه‌حل:** قبل از ذخیره در کش، پارامتر `?t=` از آدرس حذف می‌شود، پس
هر فایل داده همیشه فقط **یک** رکورد در کش دارد که هر بار جایگزین
می‌شود، نه اضافه. این هم مشکل مصرف حافظه را حل می‌کند و هم یک باگ
جانبی را: قبلاً حالت آفلاین (نمایش آخرین داده ذخیره‌شده) هم درست کار
نمی‌کرد، چون جستجوی کش هم با همان آدرس یکتا انجام می‌شد و هیچ‌وقت به
نتیجه نمی‌رسید.

یک باگ مرتبط دیگر هم در همین بررسی پیدا و اصلاح شد: `self.skipWaiting()`
به‌صورت خودکار در نصب هر نسخه جدید Service Worker اجرا می‌شد، که باعث
می‌شد صفحه بدون اجازه کاربر و بدون نمایش بنر «بروزرسانی/بعداً» یک‌بار
خودکار Reload شود. الان `skipWaiting()` فقط با کلیک روی دکمه
«بروزرسانی» اجرا می‌شود.

**نکته مهم برای اعمال این رفع باگ:** چون خود Service Worker عوض شده،
کاربرانی که همین الان پورتال را باز دارند، تا وقتی تب را کاملاً نبندند
یا روی بنر «بروزرسانی» کلیک نکنند، نسخه اصلاح‌شده را دریافت نمی‌کنند
(این هم دقیقاً همان رفتار درست و استاندارد PWA است). برای اطمینان از
پاک‌شدن سریع کش‌های قدیمیِ متورم‌شده، از همه‌ی کاربران بخواهید یک‌بار
تب پورتال را کاملاً ببندند و دوباره باز کنند.

## قابلیت‌های PWA تکمیلی (v12.1.0)

- **نصب:** دیگر دکمه نصب اختصاصی در هدر نداریم — طبق درخواست، فقط
  آیکون بومی «نصب» کنار نوار آدرس مرورگر (کنار ستاره Bookmark) استفاده
  می‌شود؛ مرورگر خودش این آیکون را نشان می‌دهد وقتی همه شرایط نصب
  برقرار باشد (پایین‌تر، بخش «نصب PWA» را ببینید — این‌جا دقیقاً همان
  چیزی توضیح داده شده که الان مانع نصب شما شده).
- **وضعیت اتصال در هدر:** یک نشانگر کوچک سبز/قرمز («متصل»/«قطع») که
  همزمان با بنر آفلاین به‌روزرسانی می‌شود.
- **آیکون‌ها:** سایزهای 192/256/384/512 + نسخه maskable و monochrome
  در `assets/icons/` اضافه شدند؛ همچنین تایل‌های ویندوز
  (`mstile-*.png`) و `browserconfig.xml`.
- **پشتیبانی اپل:** متاتگ‌های `apple-mobile-web-app-*` برای نصب روی
  iOS/Safari اضافه شدند.
- **Service Worker پیشرفته‌تر:** سه استراتژی مجزا — Stale-While-Revalidate
  برای Shell برنامه (HTML/CSS/JS)، Cache-First برای آیکون/فونت/تصویر،
  و Network-First برای `data/*.json` — با دو Cache جدا (`static` و
  `runtime`) و پاک‌سازی خودکار نسخه‌های قدیمی.
- **Stub های آماده برای آینده:** Background Sync و Push Notification
  فقط به‌صورت Stub (بدون Backend واقعی) در `service-worker.js` و
  `pwa.js` اضافه شدند تا در صورت افزودن Backend، به‌سادگی قابل تکمیل
  باشند — فعلاً هیچ کاری واقعی انجام نمی‌دهند.

## نصب PWA — چرا آیکون نصب ظاهر نمی‌شود؟ (مهم)

اگر پرتال را روی آدرسی مثل `http://192.168.184.29:8080/` باز
می‌کنید، **آیکون نصب هیچ‌وقت ظاهر نخواهد شد** — این یک محدودیت امنیتی
خودِ مرورگرهاست، نه باگ کد.

**علت:** Service Worker (که پایه‌ی نصب PWA است) فقط روی یک «Secure
Context» ثبت می‌شود: یعنی یا آدرس با **HTTPS** باشد، یا دقیقاً
`http://localhost` باشد. یک IP داخلی مثل `192.168.184.29` روی HTTP
ساده، هیچ‌کدام از این دو شرط را ندارد، پس مرورگر اصلاً اجازه ثبت
Service Worker را نمی‌دهد و به همین دلیل، معیارهای نصب PWA هرگز کامل
نمی‌شوند و آیکون نصب کنار نوار آدرس ظاهر نمی‌شود.

### دو راه‌حل واقعی

**راه‌حل ۱ (درست‌ترین، برای Production): گرفتن گواهی HTTPS**
اگر یک دامنه داخلی دارید (مثل `portal.local` که در بخش Nginx همین
پروژه تعریف شده)، یک گواهی داخلی (Internal CA) یا self-signed برای
همان دامنه بسازید و آن را روی تمام سیستم‌های بیمارستان به‌عنوان CA
معتبر Trust کنید (از طریق Group Policy در دامنه ویندوز). این تنها
راهی است که هم PWA هم سایر قابلیت‌های امنیتی مرورگر را کامل و پایدار
فعال می‌کند.

**راه‌حل ۲ (سریع، برای همین شبکه داخلی): معرفی این آدرس به مرورگر
به‌عنوان امن**
اگر گرفتن گواهی فعلاً ممکن نیست، Chrome/Edge یک تنظیم دقیقاً برای
همین سناریو دارند (شبکه داخلی، بدون امکان HTTPS واقعی):

دستی، برای یک سیستم:
1. آدرس `chrome://flags/#unsafely-treat-insecure-origin-as-secure`
   (یا در Edge: `edge://flags/#unsafely-treat-insecure-origin-as-secure`)
   را باز کنید.
2. مقابل «Insecure origins treated as secure» گزینه Enabled را بزنید.
3. در کادر متنی، آدرس دقیق را وارد کنید:
   `http://192.168.184.29:8080`
4. مرورگر را Relaunch کنید.

سراسری، برای همه‌ی سیستم‌های بیمارستان (توصیه‌شده — از طریق Group
Policy در دامنه ویندوز):
- Policy با نام `OverrideSecurityRestrictionsOnInsecureOrigin` را در
  Group Policy برای Chrome و/یا Edge (مسیر Administrative
  Templates ← Google Chrome / Microsoft Edge) فعال کنید و مقدار
  `http://192.168.184.29:8080` را به آن اضافه کنید. با این کار، تمام
  کامپیوترهای عضو دامنه، بدون نیاز به تنظیم دستی تک‌تک، این آدرس را
  امن در نظر می‌گیرند و آیکون نصب کنار نوار آدرس ظاهر خواهد شد.

بعد از هرکدام از این دو راه‌حل، صفحه را یک‌بار کامل رفرش کنید — آیکون
نصب (یک آیکون کوچک با علامت + یا مانیتور/موبایل) باید داخل نوار آدرس،
سمت راست همان محل ستاره Bookmark ظاهر شود.

### نکاتی که باید بدانید

- **جهت صفحه (`orientation`) روی `portrait` تنظیم شد**، چون صراحتاً
  خواسته شده بود. این تنظیم فقط روی نصب PWA در موبایل/تبلت اثر دارد
  (نه روی مرورگر دسکتاپ)، اما اگر پرتال روی تبلت‌های نصب‌شده به‌صورت
  landscape در ایستگاه پرستاری استفاده می‌شود، بهتر است این مقدار را
  به `"any"` در `manifest.json` برگردانید.
- **ساختار پوشه‌ها تغییر نکرد** (همچنان `assets/css`, `assets/js`,
  `data/`) — چون یکی از قوانین همان پرامپت هم «حفظ ساختار فایل‌ها»
  بود؛ ساختار پیشنهادی‌اش (`css/`, `js/`, `data/` در ریشه) با این
  قانون در تضاد بود، پس ساختار موجود حفظ شد.
- فایل `data/status.json` هنوز با شناسه‌های لینک قدیمی هماهنگ نشده
  (همان نکته‌ای که در تحویل قبلی گفته شد) — نمایشگر وضعیت سلامت
  سیستم‌ها تا وقتی این فایل به‌روزرسانی نشود، «نامشخص» نشان می‌دهد.

## قابلیت‌های جدید (v12.1)

### ۱. نمایشگر وضعیت سیستم‌ها (Health Monitor)

- منبع داده: `data/status.json` — یک آبجکت `systems` شامل `id` (باید دقیقاً
  برابر `id` همان لینک در `links.json` باشد)، `status`
  (`online` / `slow` / `offline` / `unknown`) و `responseTime` به میلی‌ثانیه.
- یک نقطه رنگی روی همان کارت موجود نمایش داده می‌شود (سبز پالس‌دار / نارنجی
  محوشونده / قرمز چشمک‌زن / خاکستری) بدون هیچ تغییری در چیدمان کارت.
- هاور روی نقطه، وضعیت، زمان پاسخ و آخرین بررسی را نشان می‌دهد.
- اگر `id` در `status.json` تعریف نشده باشد، وضعیت به‌صورت خودکار
  «نامشخص» نمایش داده می‌شود — هیچ سیستمی به‌خاطر نبود داده خراب نمی‌شود.

### ۲. به‌روزرسانی هوشمند (JSON-based administration)

- `assets/js/data-loader.js` هر بار که چهار فایل JSON را می‌خواند،
  آن‌ها را با نسخه قبلی مقایسه می‌کند و فقط بخش تغییر یافته را گزارش می‌دهد.
- در نتیجه: اگر فقط `announcement.json` تغییر کند، فقط بنر اعلان
  به‌روزرسانی می‌شود؛ اگر فقط `status.json` تغییر کند، فقط نقطه‌های وضعیت
  به‌روزرسانی می‌شوند؛ صفحه هرگز به‌طور کامل بازسازی نمی‌شود.

### ۳. نصب به‌عنوان اپلیکیشن (PWA)

- `manifest.json` و `service-worker.js` پورتال را قابل‌نصب روی ویندوز،
  اندروید و تبلت می‌کنند (آیکون نصب در مرورگرهای Chrome/Edge/Firefox
  ظاهر می‌شود).
- در حالت آفلاین، آخرین داده بارگذاری‌شده (لینک‌ها، اعلان، وضعیت) از
  کش سرویس‌ورکر نمایش داده می‌شود و بنر «ارتباط شبکه قطع است» دیده می‌شود.
- هنگام هر دیپلوی، به همراه بالا بردن نسخه در `index.html` و
  `config.json`، مقدار `CACHE_VERSION` در `service-worker.js` را هم
  افزایش دهید؛ سرویس‌ورکر کش قدیمی را خودش حذف و به کاربر بنر «نسخه
  جدید آماده است» با دکمه بازخوانی نشان می‌دهد.
- آیکون‌های PWA در `assets/icons/icon-192.png`, `icon-512.png` و
  `icon-maskable-512.png` قرار دارند؛ در صورت نیاز به لوگوی رسمی
  بیمارستان، همین فایل‌ها را با همان نام و اندازه جای‌گزین کنید.
